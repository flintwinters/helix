# Helix

Helix is fundamentally a native C++ system, not a VM language, transpiler target, or managed runtime. The implemented runtime currently interprets YAML object graphs as structured cells with a `main` entrypoint, symbolic string resolution, builtin forms, mutable VM state, stepping, child VM execution, includes, signals, and fixture tests; these are early mechanisms for the broader microVM idea. The planned architecture treats recursively nestable microVMs as small, isolated, message-passing computational objects: each owns structured state, exposes addressable namespaces, can be inspected, versioned, paused, stepped, and potentially scheduled under deterministic or non-linear time. YAML is the universal representation and interface layer rather than the final storage or performance model: files, devices, services, packages, debugger views, and low-level C++ resources are intended to appear as structured, addressable objects. The design is inspired by Plan 9 namespaces, capability systems, actor models, version control systems, databases, deterministic simulators, and theorem provers, without being directly dependent on any of them. State versioning, replay, branching histories, loose protocol-driven communication, capability declaration, discovery by behavior, and optional formal verification are recurring themes. The long-term goal is to blur the boundaries between operating system, runtime, database, debugger, package manager, and version control system around versioned object graphs and programmable state.
